## 1. 问题影响

### 报告交叉摘要

第一次缺少有效表单 token 的请求返回 302，不作为漏洞证据。随后使用有效会话上传唯一临时 PHP 探针，访问结果显示 PHP 标记和无害 `id` 输出；探针已删除，容器检查确认不存在，原有 `dvwa_email.png` 保留。

## 3. 核心代码位置

### 报告交叉摘要

`vulnerabilities/upload/source/low.php` 的上传接收、命名、移动逻辑；上传目标为 `hackable/uploads/`。

### 原记录：目标与源码发现

仅在本机 DVWA Low File Upload（`http://127.0.0.1:4280`）进行。原始 `low.php` 仅对客户端文件名调用 `basename()`，随后直接 `move_uploaded_file()` 到 Web 可访问的 `hackable/uploads/`；没有服务端扩展名、MIME、内容或解析限制。证据副本见 `evidence/low-before.php`。

## 4. 脱敏请求与证据

### 原记录：漏洞验证（实测）

最初的 curl 请求因缺少有效 `user_token` 返回 302，未到达上传处理逻辑；这次失败不作为漏洞证据。随后验证脚本从登录页取得 token、登录并设为 Low，先确认唯一目标文件不存在，再仅上传一次临时 `hermes-rce-probe.php`。页面返回上传成功，随后读取上传 URL：脚本确认 PHP 标记已执行、响应含 `id` 命令输出，并打印 `RCE_PROBE_VERIFIED`。这证明本机 DVWA Low 的上传目录允许 PHP 执行及命令执行。

脚本 `scripts/verify_upload_rce.py` 在 `finally` 中删除该唯一文件；它报告 `REMOVED`。之后容器目录检查确认临时 PHP 文件不存在，原有 `dvwa_email.png` 仍在。没有改动 DVWA 上游容器源码，没有留下 Web Shell。

## 5. 漏洞根因

### 报告交叉摘要

Low 主要对文件名做路径层面的 `basename()` 处理，缺少可靠内容校验，并把文件放在 Web 可访问目录；若服务器会解析上传目录中的 PHP，上传即变成代码执行入口。

## 6. Patch diff 与修复建议

- 补丁文件：[`fix.patch`](fix.patch)；完整 diff 保留在该文件，是否部署仍以本篇状态记录为准。

### 报告交叉摘要

服务端确认内容格式，若业务只收图片则实际解码并重新编码；随机生成存储名；将上传文件放在 Web 根目录外，或以不可执行方式静态提供；限制权限、大小、类型和下载响应头。

### 原记录：修复与复测

`fix.patch` 对应 `source/low.php`，只在 `worktree/` 源码副本应用，未部署到运行中的 DVWA。修复要求上传必须是大小和像素数受限的 JPEG/PNG，经 GD 解码并重新编码为 PNG；服务器生成随机名称，存到 Web 根目录之外的私有目录，不直接返回可访问路径。客户端文件名、扩展名和 MIME 声明均不作为信任依据。

验证结果：补丁 dry-run 与应用通过；补丁后 PHP 文件在 DVWA 容器 PHP CLI 中 `php -l` 通过。直接调用补丁中的处理函数，原有 PNG 样本被接受并重新编码为 PNG；文本探针被拒绝且未生成输出文件。未将补丁部署到 DVWA，也未做页面级修复后 HTTP 复测。
